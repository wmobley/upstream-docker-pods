## Key Learnings

- **Project:** upstream-docker-pods
- **Description:** [![DOI](https://zenodo.org/badge/1076824318.svg)](https://doi.org/10.5281/zenodo.17664688)
- **[2026-07-17] Two distinct permission systems exist and must not be conflated:** Tapis pod/stack permission (ADMIN/USER/READ, infra-ops control — who can start/stop/delete a pod, granted via `set_pod_permission`/`set_stack_permission` in `app/services/pods_service.py`) vs. the app's own per-project DB `user_roles` table (NONE/READ/USER/APPROVEDADMIN/ADMIN, data-access control — resolved by `resolve_user_role()` in `app/api/dependencies/auth.py` and enforced via `get_viewer_user`/`get_edit_user`/`get_admin_user`). They share similarly-named levels but answer different questions. Any user-facing "what can I do in this project" UI should read the DB role, not Tapis's pod permission.
- **[2026-07-17] `get_current_user` accepts a raw Tapis RS256 access token directly as a Bearer header** (`app/api/dependencies/auth.py` ~line 203) — no Upstream-JWT exchange needed. This means any client already holding a Tapis token can call any authenticated endpoint on any project's API pod and get back that project's DB-resolved role/identity for free.
- **[2026-07-17] `TAPIS_ENFORCE_AUTH_IN_DEV` (default `false`) exists specifically to let `ENV=dev` deployments opt into real auth enforcement** — `authenticate_user()` already checked it; `get_current_user()` didn't until this date. Check both when touching dev-mode auth bypass logic.
- **[2026-07-17] Tests run against this repo's checked-in `.env`, which has `ENV=dev` and `TAPIS_ENFORCE_AUTH_IN_DEV=false`.** A test asserting "unauthenticated request returns 401" against the *real* `get_current_user` dependency (not an override) will silently pass through the dev bypass and return 200 unless the test explicitly monkeypatches `TAPIS_ENFORCE_AUTH_IN_DEV=True` first.
- **[2026-08-13] CKAN allocation checks normalize org identifiers before authorization:** `_fetch_user_organizations()` lowercases/trims CKAN org id/name/display/title, so `check_allocation_permission()` must normalize `Campaign.allocation` before exact comparison. Without that, station/list read routes that enforce allocation can 404 even when campaign detail loads.
- **[2026-08-13] CKAN dataset conflict policy:** `package_create` 409 can be recoverable when the existing CKAN dataset extras match the same Upstream campaign/station. Upload and station-create paths keep idempotent patch behavior; explicit station publish defaults to conflict-first and requires `patch_existing_ckan_dataset=true` to patch a matching dataset. `ckan_dataset_name` lets callers choose a suggested alternate name.
- **[2026-08-13] CKAN publish dataset identity with shared UI links:** `build_station_dataset_identity()` must derive `upstream_dataset_key`/hash/name from the base station URL without `?project=...`; only the CKAN `source`/resource UI URLs should append `project=<STACK_ID>`. Otherwise a shared multi-project link would create duplicate CKAN datasets for already-published stations.
- **[2026-08-14] The CSV upload endpoint now supports chunked upload sessions.** Clients send `upload_session_id` + `chunk_index` + `total_chunks` + `finalize_upload` form fields (all optional; defaults keep legacy single-request behavior). Measurements are inserted per chunk; sensor-statistics/geometry refresh and CKAN sync run only once, after the server verifies successful receipts for every chunk index. Responses include an `audit` block (rows_read/values_attempted/values_inserted/values_skipped_duplicate/sensor_alias_count/row_errors) plus legacy keys. `skipped_duplicate = attempted - inserted` only holds because the sole `ON CONFLICT DO NOTHING` path is `(sensorid, collectiontime)`.
- **[2026-08-14] FastAPI parameter ordering gotcha:** a `BackgroundTasks` parameter declared *after* defaulted `Form`/path params causes `SyntaxError: non-default argument follows default argument`. Declare `background_tasks` before any defaulted form params (right after required `File` params).
- **[2026-08-14] Migration heads:** this repo has 3 alembic heads on main (`778a9dbdeb5e`, `c6b888362baa`, `d4e5f6a7b8c9`); new migrations must be merge migrations. Production startup runs `alembic upgrade heads` (plural). Verify migrations against a real Postgres with PostGIS — plain Postgres lacks the `geometry` type; offline `alembic upgrade --sql` also fails on the geometry server_default in an older migration.
- **[2026-08-14] UI API client regen is blocked locally:** `openapi-generator-cli` is not installed in `upstream-ui` and `npx --no-install` fails, so the generated `UploadfileCsvApi` cannot model the new form fields. The chunked upload path uses a typed `fetch` wrapper (`postUploadChunk`) in `useUploadData.ts`; regeneration via `update-upstream-api-client.sh` is a follow-up.

- [2026-07-17] Don't write a "requires authentication" test against `get_current_user`'s real dependency without first checking `.env`'s `ENV`/`TAPIS_ENFORCE_AUTH_IN_DEV` values — this repo's dev-mode bypass will make the request succeed instead of 401ing, producing a false-negative test that looks like it's testing auth but isn't. Monkeypatch `TAPIS_ENFORCE_AUTH_IN_DEV=True` in the test.
- [2026-07-21] Commit `2c8932e` ("set API pod CORS at bundle-creation time, not after") assumed baking `cors_allow_origins` into the initial `create_pod()` POST payload avoids Tapis's APPROVEDADMIN gate, "since that only applies to editing an existing pod's networking, not the creator's own initial config." This assumption is wrong: the gate applies to creation too, since the acting identity (the end user's own forwarded Tapis token, per `PodsService(token_override=tapis_token)` in `pods.py`) doesn't hold APPROVEDADMIN. Result: `POST /api/v1/pods/bundle` now hard-fails bundle creation entirely (previously only the later CORS PUT failed, and the pod itself still got created). Don't assume Tapis permission gates are edit-only without testing creation too — and don't bake permission-gated fields into a create payload as a workaround without confirming the acting token already holds the required permission.
- [2026-07-21] Retrying `build_bundle()` with a `base` name that partially succeeded before (e.g. postgres pod created, api pod failed) hits `create_pod()`'s lack of idempotency — unlike `create_stack()`/`create_volume()`, it didn't treat "already exists" as success, so it raised a raw Postgres `IntegrityError`/`UniqueViolation` through to the API's 502 response (bug-003). When adding new pod-creation error handling in `create_pod()`, check "already exists"/"uniqueviolation" first (mirroring stack/volume), since any partial-failure retry will always hit this on the pods that did get created.
- [2026-07-21] Never issue a raw `op.execute("CREATE TYPE ... AS ENUM (...)")` in the same Alembic migration that also declares a column as `sa.Enum(..., name="...")` inside `create_table()` — the Enum column's own DDL already emits `CREATE TYPE` as part of table creation, so both statements collide in the same transaction with `psycopg.errors.DuplicateObject` on every fresh database (bug-004, `a1b2c3d4e5f6_add_notes_table.py`). Since this repo's pod startup command loops `alembic upgrade heads` with a retry-until-success sleep loop, a deterministic migration failure like this wedges pod startup forever, not just once. When touching a migration with Postgres ENUM columns, verify against a real `postgis/postgis:<tag>` container (plain `postgres` image lacks the `geometry` type other migrations in this repo depend on) rather than assuming from the diff — `docker run -p <port>:5432 -e POSTGRES_PASSWORD=... -e POSTGRES_DB=... postgis/postgis:17-3.5` then `DATABASE_URL=... alembic upgrade heads`.
- [2026-07-21] CI's `pytest` job also runs `mypy .` as a required step — verifying a fix by only running pytest locally isn't enough; a mypy-clean pytest pass can still fail CI (happened with `_grant_or_log`'s untyped `grant_fn` param and an uninferable lambda default-arg). Always run `mypy .` locally alongside pytest before pushing/cherry-picking to main, not just after CI reports failure.
- [2026-07-21] Commits on this repo can sit local-only for a while — before assuming a "fix" is live for the user to test, check `git log origin/main..HEAD` and the deploy workflow's trigger branch. `2c8932e` and this session's own subsequent fix commits were never pushed, so a user re-reporting the identical original error after "testing" was actually just hitting the still-deployed pre-`2c8932e` code, not a regression in the new fix. Don't assume a local code change has taken effect for the user without confirming push + deploy state first.

- [2026-07-21] `.env.sample` had a stale `TAPIS_BASE_URL=https://tacc.tapis.io` / `TAPIS_TENANT_ID=tacc` pair that didn't match every other default in the repo (`config.py`, deploy workflow, `pods_service.py` all use `portals.tapis.io`/`portals`). Confirmed with user: `portals` is correct. Fixed the sample (be092ad/3175c50), but this does NOT fix any already-deployed pod whose actual env var was set from the stale sample — that requires checking/correcting the live pod's real `TAPIS_TENANT_ID` on Tapis directly (outside this repo's control) and redeploying.

- [2026-07-22] After bug-002 through bug-005 (create-payload CORS baking, service-account self-grant, ordering fix) all failed to resolve Tapis's "Not authorized -- you do not have access to this endpoint" on POST /pods/{pod_id}/permissions — despite confirming tenant id, logged-in user, and service username all matched expectations — the user decided to abandon in-app CORS/APPROVEDADMIN automation entirely rather than keep debugging blind against live Tapis authorization internals with no direct visibility into them. build_bundle() no longer attempts CORS or APPROVEDADMIN at all; that remains a manual, out-of-band step via update_cors_all.py/update_cors.py or direct Tapis admin action. Don't re-attempt automating this without first getting direct access to Tapis's own authorization logs/support to understand why the grant is rejected — guessing from the client side alone did not converge after 4 attempts.

- [2026-07-22] Added TAS-allocation-based role elevation, gated strictly to the primary upstreamapi via a new `IS_PRIMARY_INSTANCE` setting (bundle-created project pods never set this). Discovered along the way: `app/pytas/` (the TAS REST client) was dormant/broken dead code — `TASClient()` is called with zero args everywhere but its `__init__` required `credentials["username"]` with no fallback, so it crashed immediately with a NoneType error the moment anything actually called it. Fixed the credential defaulting as part of this feature. Also: `app/pytas/*` is excluded from mypy (`mypy.ini`'s `exclude`), so the first cross-boundary import from it (`app/services/tas_service.py`) needed a `[mypy-app.pytas.*]` override with `follow_imports = skip` to avoid a false "has no attribute" error — remember this if anything else ever imports from `app/pytas/`.
- [2026-07-22] `app/core/config.py`'s `ALLOWED_ALLOCATIONS` setting looked related to TAS allocations but is actually dead/unused — the real "allocation" concept already wired up in this repo (`app/api/dependencies/pytas.py`, despite its name) means CKAN organization membership, not TAS project allocations. These are two unrelated concepts that happen to share the word "allocation" — don't conflate them.
- [2026-08-13] Do not compare raw `Campaign.allocation` to CKAN organization identifiers. The CKAN side is normalized; use exact normalized comparison on both sides and keep the existing empty-allocation fallback for CKAN-disabled/read-only paths.
- [2026-08-13] Do not log CKAN `package_create` 409 as an ERROR before conflict classification. It may be the expected first step in create-or-patch idempotency; classify it, suggest a new name when failing, and patch only when the caller/path explicitly allows it.
- [2026-08-13] After merging main into `feature/contextual-notes`, do not assume conflict-free files are semantically correct: main renamed `app.api.dependencies.pytas` to `ckan`, leaving the branch's new `tests/api/dependencies/test_pytas.py` import stale, and main's optional public measurement access meant tests had to mock station/sensor repositories instead of letting TestClient hit real SQLite through `get_db`.
- [2026-08-14] In the upload CSV route, cache `upload_event_id` right after creating the receipt instead of reading `upload_event.id` again in `except` handlers after `db.rollback()` — the ORM object is expired post-rollback and attribute access can raise. Same for the old inline-CKAN block: never pass request-scoped ORM objects to a `BackgroundTasks` function.
- [2026-08-14] `pd.read_csv` on an empty file raises `pd.errors.EmptyDataError` (sensors-only uploads send an empty measurements blob) — catch it and return a zero-row result instead of a 500. Also the pandas dtype dict must be `{'Lon_deg': 'str', 'Lat_deg': 'str'}` to keep geometry strings intact.
- [2026-08-14] SQLAlchemy `default=False` on a mapped column does NOT set the attribute on object construction — it's applied at flush. A unit test asserting `event.finalized is False` right after `UploadFileEvent(...)` fails (it's `None`); assert `not event.finalized` instead.
